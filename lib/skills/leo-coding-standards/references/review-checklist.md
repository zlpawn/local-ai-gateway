# Java 代码审查清单

## 审查顺序

按风险从高到低检查：

1. 正确性、安全性、并发和资源管理。
2. Java 版本与依赖兼容性。
3. API 语义、空值、空白字符串、集合和 `Optional`。
4. 类、方法和接口职责。
5. 异常、日志和敏感信息。
6. 可测试性和测试代码质量。
7. 可读性、重复及设计模式使用。

不要因为低优先级风格差异分散对高风险缺陷的注意力。

## 问题等级

- `P0`：可能导致安全事故、数据损坏或系统整体不可用。
- `P1`：明确功能错误、资源泄漏、并发缺陷、异常契约破坏或敏感信息泄露。
- `P2`：明确违反 `MUST`，或违反 `SHOULD` 并造成具体维护、扩展、可读性或测试成本。
- `P3`：局部命名、结构或可读性问题，修复收益明确但不影响当前行为。

未采用 `CONSIDER` 不构成问题。未使用某个首选 API 也不自动构成问题。

## 每条发现必须包含

- 优先级和简短标题。
- 精确文件和行号。
- 当前代码造成的具体影响。
- 触发问题的输入、状态或执行场景。
- 最小范围的修复建议。

示例：

```text
[P2] 空值判断未覆盖仅含空白字符的名称
UserService.java:48

当前使用 `name == null || name.isEmpty()`，输入 `"   "` 时会被视为有效名称。
项目已包含 Commons Lang，应使用 `StringUtils.isBlank(name)`，使校验语义与规范一致。
```

## 报告约束

- 先列发现，再写简短摘要。
- 不报告没有具体影响的个人偏好。
- 不建议为了规范新增第三方依赖。
- 不要求一次整改所有旧代码。
- 不建议与当前任务无关的大范围重构。
- 存在合理例外时，接受更直接或更符合项目局部风格的实现。
- 修复建议保持最小范围，不借审查扩张需求。
- 未发现问题时明确说明，并指出尚未覆盖的测试或验证风险。
- 本 skill 不主动运行编译、测试、格式化或静态分析；不要把“未运行”误写为代码缺陷。

## 快速判断

报告前确认：

1. 这是否会在现实输入或状态下造成问题？
2. 这是违反契约，还是仅与个人偏好不同？
3. 是否能指出具体文件、行号和触发条件？
4. 建议是否比当前代码更简单或更可靠？
5. 修复是否属于当前任务范围？

无法说明具体影响时，不要创建 finding。
