## MUST

- 让每个方法具有一个清晰的主要意图。
- 不得吞掉异常、保留空 `catch`，或通过捕获 `Throwable` 掩盖系统错误。
- 不得记录密码、Token、密钥、身份证号等敏感信息。
- 不得使用异常控制正常业务流程。
- 覆写 `equals()` 时同步评估并通常覆写 `hashCode()`。
- 使用 `try-with-resources` 或等效机制可靠释放资源。
- 不得为了应用设计模式而改变正确的业务语义。
- 让核心业务逻辑能够脱离不稳定的外部依赖独立测试。

## SOLID

### SRP：单一职责

- 让类和方法只承担一个主要职责，并保留同一抽象层级。
- 当一个方法同时负责查询、决策、转换和持久化时，考虑按职责拆分。
- 不要只凭行数拆分类或方法；以业务意图和变化原因作为判断依据。

### OCP：开闭原则

- 对已经出现的变化点开放扩展，例如多种定价、校验或路由规则。
- 增加新变体时，优先让扩展发生在稳定边界之外。
- 只有一个稳定实现时，不要为假设中的未来需求预建扩展体系。

### LSP：里氏替换

- 让子类型维持父类型的前置条件、后置条件和可观察行为。
- 不要通过更严格的输入限制或无意义的 `UnsupportedOperationException` 破坏父类型契约。
- 如果子类型无法履行契约，重新审视继承关系，优先组合或拆分接口。

### ISP：接口隔离

- 按调用者实际需要设计专门接口。
- 不要迫使实现类依赖或实现无关方法。
- 拆分接口时保持业务概念完整，不追求每个接口只有一个方法。

### DIP：依赖倒置

- 让核心业务依赖稳定抽象，不直接绑定可替换的网络、存储或供应商实现。
- 在真实替换点、测试边界或外部系统边界引入接口。
- 不要仅为了“面向接口”给每个类配一个没有第二实现价值的接口。

## LoD、KISS 与 DRY

### LoD：迪米特法则

- 避免穿透多层对象图并修改远端状态。
- 将行为放到真正拥有相关数据和规则的对象中。
- 不要为了消除所有链式调用而增加无业务意义的转发方法。

### KISS

- 优先清晰、直接、容易验证的实现。
- 用早返回减少深层嵌套，但保持控制流连续、可读。
- 不引入当前需求不需要的配置项、扩展点或抽象层。

### DRY

- 当重复代码表达稳定的共同业务知识时提取复用。
- 仅代码形状相似但业务含义不同的逻辑，不要强行合并。
- 不要为了消除少量无害重复而引入更难理解的抽象。

## 通用编码规则

### 命名与结构

- 使用能表达业务含义的名称，避免无上下文的 `data`、`info`、`obj`、`temp`。
- 方法名使用动词或动词短语；布尔值名称表达判断语义。
- 将稳定业务值提取为有含义的常量，避免魔法值。
- 保持同一方法中的抽象层级一致。
- 优先组合而非为复用少量实现细节建立继承层级。

### 异常

- 在能够补充上下文或转换抽象层级的位置处理异常。
- 转换异常时保留根因，例如将原异常传入新异常构造器。
- 捕获具体异常，不用宽泛捕获隐藏编程错误。
- 错误消息包含定位问题所需的业务上下文，但不泄露敏感数据。

### 日志

- 使用参数化占位符，不为日志提前拼接字符串。
- 在最能采取行动的边界记录异常，避免多个层级重复打印同一堆栈。
- 正常业务分支不要记录为 `ERROR`。
- 日志内容保持可检索，包含稳定标识和必要上下文。
- 脱敏或省略凭据、个人敏感信息和大体积对象。

### 注释

- 解释原因、约束、契约和非显然权衡，不复述代码。
- 代码变化后同步更新仍有价值的注释。
- 优先通过命名和结构表达意图；不要用注释掩盖复杂实现。

### 可测试性

- 将时间、随机数、网络、持久化和其他不稳定依赖放在可替换边界后。
- 让业务规则可以通过确定性输入和输出验证。
- 测试代码遵循与生产代码相同的命名、结构和重复控制要求。
- 不为了测试暴露无业务意义的 public 方法。

## 设计模式

设计模式属于 `CONSIDER`。先证明当前复杂度和变化点，再选择模式。

| 已出现的问题 | 可考虑的模式 |
|---|---|
| 多种可替换算法、计费或校验规则 | Strategy |
| 创建过程复杂或需要隔离具体类型 | Factory、Builder |
| 流程骨架稳定但部分步骤变化 | Template Method |
| 多个处理器按顺序匹配或处理 | Chain of Responsibility |
| 多个对象需要响应明确事件 | Observer |
| 接口不兼容但需要复用现有实现 | Adapter |
| 不改变核心对象而增加横切行为 | Decorator |

引入模式前回答：

1. 当前具体的变化点或复杂度是什么？
2. 直接实现为什么已经不足？
3. 模式是否减少条件分支、耦合或有意义的重复？
4. 新抽象是否比原问题更容易理解、测试和维护？

只有一个实现、一个简单分支或尚无真实变化点时，保持直接实现。不要用模式数量衡量代码质量。
